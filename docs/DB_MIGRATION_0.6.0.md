# 0.6.0 반입 및 데이터 보관/정리 안내

## 1. 이번 버전의 변경 사항

- 칸반 카드에서 TODO를 수정할 수 있습니다. 공용 TODO는 등록자가 아니어도 칸반에서 제목, 담당자, 마감일, 비고를 수정할 수 있습니다.
- 메인 페이지 TODO 등록 폼에서는 담당자 입력을 제거했습니다. 등록 시 담당자는 본인으로 지정됩니다.
- 칸반 페이지에서는 제목만 입력해 공용 TODO를 추가합니다. 담당자는 등록자 본인으로 지정되며, 나머지는 카드의 '수정'에서 입력합니다.
- TODO 공개 범위 기본값은 공용입니다.
- 메인 캘린더 아래에 오늘 해야 할 일을 표시합니다. 본인이 등록한 일정 또는 본인이 담당자로 지정된 일정 중 휴가를 제외하고, 본인이 등록했거나 담당자인 진행 중 TODO를 표시합니다.
- 버전은 0.6.0입니다.

기존 DB 구조에 새 컬럼을 추가하지 않습니다. 이전 0.5.x에서 추가한 `users.deleted_at`, `todos.note`는 그대로 사용합니다. 기존 데이터는 자동 초기화하거나 변환하지 않습니다.

## 2. 코드 반입

1. 서버를 종료합니다.
2. 기존 프로젝트의 `app/main.py`를 백업합니다.
3. 반입 패키지의 `app/main.py`로 교체합니다.
4. `scripts/maintenance_archive.py`를 기존 프로젝트의 `scripts` 폴더에 복사합니다.
5. 기존 `data` 폴더와 `data/calendar.db`, `data/uploads`는 그대로 둡니다.
6. 기존 실행 명령으로 재시작합니다.

```powershell
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000
```

이번 버전은 새 DB 마이그레이션을 요구하지 않습니다. 별도 SQL을 실행하지 마세요.

## 3. 3개월 지난 데이터 보관 및 정리 스크립트

파일: `scripts/maintenance_archive.py`

이 스크립트는 Python 표준 라이브러리만 사용하므로 별도 패키지 설치가 필요하지 않습니다. 기본 DB 위치는 앱과 동일한 `data/calendar.db`이며, `CALENDAR_DATA_DIR` 환경변수도 지원합니다.

### 먼저 미리보기

프로젝트 루트에서 실행합니다.

```powershell
python scripts/maintenance_archive.py
```

기본 실행은 삭제하지 않고 정리 대상 건수만 보여줍니다.

### 실제 백업 및 정리

미리보기 결과를 확인한 후 다음 명령을 실행합니다.

```powershell
python scripts/maintenance_archive.py --apply
```

보관 기간을 변경하려면 `--months`를 사용할 수 있습니다. 기본값은 3개월입니다.

```powershell
python scripts/maintenance_archive.py --months 3 --apply
```

### 백업 파일과 확인 방법

실행하면 먼저 다음 위치에 ZIP 백업을 생성합니다.

```text
data/
  archives/
    calendar_archive_YYYYMMDD_HHMMSS.zip
```

ZIP에는 다음이 포함됩니다.

- `calendar.db`: 정리 전 SQLite 전체 백업본
- `uploads/`: 첨부파일 원본 전체
- `ARCHIVE_INFO.txt`: 백업 생성 시각과 정리 기준일

SQLite WAL 모드를 고려해 Python SQLite Backup API로 일관된 스냅샷을 만들고, 백업 DB의 `PRAGMA integrity_check`가 `ok`인지 확인한 다음에만 정리를 진행합니다.

나중에 확인하려면 ZIP을 별도 폴더에 압축 해제한 뒤 `calendar.db`를 DB Browser for SQLite 또는 SQLite 도구로 열면 됩니다. 백업 당시 첨부파일은 같은 폴더의 `uploads`에서 확인할 수 있습니다. 백업 ZIP은 자동 삭제하지 않으므로 용량을 확인해 별도 저장소에 보관하세요.

### 정리되는 데이터 기준

| 데이터 | 현 DB에서 삭제되는 기준 |
|---|---|
| 일정 | 종료일(종료일이 없으면 시작일)이 3개월보다 오래된 일정 또는 3개월보다 오래전에 휴지통으로 이동한 일정 |
| TODO | 3개월보다 오래전에 삭제된 TODO 또는 생성된 지 3개월이 넘은 완료 TODO |
| 댓글 | 생성일이 3개월보다 오래된 댓글 |
| 활동 로그 | 생성일이 3개월보다 오래된 로그 |
| 사용자 | 삭제하지 않음 |
| 미완료 TODO | 오래되었더라도 삭제하지 않음 |

일정 삭제 시 연결된 댓글 및 첨부파일 메타데이터도 DB의 외래키 규칙에 따라 함께 삭제됩니다. 해당 일정의 첨부파일 원본은 ZIP 백업에 보관한 뒤 현재 `uploads`에서 제거합니다.

### 운영 권장 순서

- 처음에는 반드시 미리보기 명령으로 삭제 예정 건수를 확인합니다.
- 운영 데이터가 적은 시간에 `--apply`를 실행합니다.
- 백업 ZIP이 정상 생성되었는지 확인하고, 별도 서버/공유 폴더에도 복사합니다.
- 백업 ZIP을 열어 `calendar.db`와 `uploads`가 있는지 확인합니다.
- 정리 후 캘린더, TODO, 칸반, 첨부파일을 확인합니다.

SQLite Backup API를 사용하므로 DB 스냅샷은 일관되게 생성됩니다. 다만 DB 백업과 첨부파일 복사 사이의 파일 변경까지 하나의 원자적 스냅샷으로 묶을 수는 없으므로, **가장 안전한 방법은 서버를 종료한 상태에서 스크립트를 실행하는 것**입니다. 운영상 서버를 종료할 수 없다면 사용량이 적은 시간에 실행하고, 첨부파일 백업도 확인하세요. 정리 중 오류가 발생하면 DB 삭제 트랜잭션은 롤백됩니다.

## 4. 복구 및 주의 사항

정리 전 상태로 전체 복구하려면 서버를 종료하고 백업 ZIP의 `calendar.db`와 `uploads`를 기존 데이터 폴더에 함께 복원해야 합니다. DB만 복원하고 첨부파일 폴더를 복원하지 않으면 과거 첨부파일을 열 수 없습니다.

백업 ZIP은 개인정보와 업무 정보가 포함될 수 있으므로 접근 권한이 제한된 위치에 보관하고, 사내 보안 정책에 따라 관리하세요.
