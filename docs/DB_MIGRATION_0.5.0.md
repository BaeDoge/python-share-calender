# 기존 DB를 유지한 채 0.5.x 적용하기

이 문서는 기존 사내 서버의 일정, TODO, 사용자, 댓글, 첨부파일을 유지하면서 새 버전의 `app/main.py`를 반입하는 절차입니다.

## 이번 버전의 DB 변경

서버가 시작될 때 `init_db()`가 기존 SQLite DB의 스키마를 확인하고 필요한 컬럼만 추가합니다.

| 테이블 | 추가 컬럼 | 목적 |
|---|---|---|
| `users` | `deleted_at TEXT` | 계정 비활성화(소프트 삭제) |
| `todos` | `note TEXT NOT NULL DEFAULT ''` | TODO 비고 |

- 기존 사용자, 일정, TODO, 댓글, 첨부파일 메타데이터는 삭제하지 않습니다.
- 기존 TODO의 `priority` 컬럼은 호환성을 위해 DB에 남겨 둡니다. 새 화면과 API에서는 우선순위를 사용하지 않습니다.
- 기존 TODO의 새 `note` 값은 빈 문자열로 시작합니다.
- 기존 TODO의 담당자(`assignee_id`)와 진행 상태 마이그레이션은 기존 동작을 유지합니다.
- 관리자에서 계정을 삭제하면 사용자 레코드를 물리 삭제하지 않고 `deleted_at`을 기록합니다. 일정·TODO·댓글·첨부파일의 작성자 참조와 이력은 보존됩니다.

## 반입 전 백업

1. 현재 서버를 실행 중인 터미널에서 `Ctrl+C`로 정상 종료합니다.
2. 프로젝트 루트의 `data` 폴더 전체를 별도 백업 위치에 복사합니다. 기본 경로라면 다음 파일과 폴더가 포함되어야 합니다.
   - `data/calendar.db`
   - `data/uploads/` (일정 첨부파일 원본)
3. `CALENDAR_DATA_DIR` 환경변수를 사용 중이면 프로젝트의 `data`가 아니라 해당 환경변수 경로를 백업합니다.
4. 필요하면 `logs/`도 별도로 백업합니다.

> SQLite가 WAL 모드이므로 실행 중인 상태에서 DB 파일만 복사하지 마세요. 서버를 먼저 정상 종료한 뒤 데이터 폴더 전체를 복사해야 합니다.

## 코드 반입

1. 반입 ZIP의 `app/main.py`를 기존 프로젝트의 `app/main.py`에 덮어씁니다.
2. `docs/DB_MIGRATION_0.5.0.md`는 참고 문서이므로 기존 프로젝트의 `docs` 폴더에 보관하면 됩니다.
3. **기존 `data` 폴더, `calendar.db`, `uploads`를 삭제하거나 새 빈 폴더로 교체하지 마세요.**
4. `pyproject.toml`, `uv.lock` 및 실행 환경은 변경할 필요가 없습니다.

## 서버 재시작 및 자동 마이그레이션

기존과 동일한 명령으로 실행합니다.

```powershell
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000
```

첫 시작 시 다음 컬럼이 없는 경우에만 자동으로 추가됩니다.

- `users.deleted_at`
- `todos.note`

이 작업은 기존 레코드를 초기화하지 않습니다. 마이그레이션은 앱 시작 시 자동 수행되므로 별도의 SQL을 실행할 필요가 없습니다.

## 적용 후 확인

다음 순서로 간단히 확인하세요.

1. 기존 캘린더의 일정과 첨부파일이 그대로 보이는지 확인합니다.
2. 기존 TODO가 그대로 보이고, 비고가 빈 값으로 표시되는지 확인합니다.
3. 새 TODO를 등록하고 Enter 키로도 등록되는지 확인합니다.
4. TODO 수정에서 제목, 담당자, 마감일, 공개 범위, 비고가 저장되는지 확인합니다.
5. TODO가 9개 이상이면 메인 화면에서 페이지 이동이 가능한지 확인합니다.
6. 칸반에서 새 TODO를 추가하고 담당자 행에 표시되는지 확인합니다.
7. 관리자 페이지의 사용자 목록에서 테스트 계정을 비활성화하고, 칸반 및 담당자 선택 목록에서 제외되는지 확인합니다.
8. 이름 입력을 취소하거나 공백만 입력했을 때 캘린더 진입이 차단되는지 확인합니다.

SQLite CLI가 설치되어 있다면 서버를 종료한 상태에서 무결성을 확인할 수 있습니다.

```powershell
python -c "import sqlite3; c=sqlite3.connect('data/calendar.db'); print(c.execute('PRAGMA integrity_check').fetchone()[0])"
```

정상 결과는 `ok`입니다. `CALENDAR_DATA_DIR`를 사용한다면 명령의 DB 경로를 실제 경로로 바꾸세요.

## 문제 발생 시 롤백

1. 서버를 종료합니다.
2. 반입 전 백업해 둔 기존 `app/main.py`와 `data` 폴더 전체를 함께 복원합니다.
3. 서버를 기존 실행 명령으로 다시 시작합니다.

이번 버전에서 DB 컬럼이 추가되므로 **코드만 이전 버전으로 되돌리지 말고, 백업한 DB도 함께 복원**해야 합니다. 이전 코드가 기존 users 테이블을 6개 값의 위치 기반 INSERT로 작성한 경우 추가 컬럼이 있는 DB와 호환되지 않을 수 있습니다.

## 계정 삭제 동작에 대한 참고

관리자 페이지의 계정 삭제는 실제 SQL `DELETE`가 아니라 계정 비활성화입니다. 기존 일정과 TODO의 작성자, 댓글 작성자, 첨부파일 업로더 이력을 유지하기 위한 설계입니다. 비활성화된 사용자는 일반 사용자 인증과 담당자 선택에서 제외됩니다. 해당 브라우저의 기존 식별자는 유지되므로 관리자가 계정을 복구하면 같은 브라우저에서 다시 접속할 수 있습니다. 관리자 페이지의 사용자 목록에서 비활성화된 계정은 '계정 복구'로 되돌릴 수 있습니다.
